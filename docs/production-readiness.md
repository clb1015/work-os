# Production readiness audit

Audit date: October 4, 2026. Canonical repository, deployment and Supabase project preserved. AI and embeddings were not added.

## Working correctly

- Production email/password sign-in succeeded with the authorized account. The pre-fix Board matched all 17 Supabase work items: Active 10, Waiting 2, Review 3, Inbox 1, Done 1.
- All ten public tables have owner-based RLS, including UPDATE WITH CHECK. One auth user exists. No service-role key or direct browser database/auth client is used.
- Database boundary probes verified anonymous reads denied, other-owner reads return no work items, and a write against the real owner's ID is denied. All probes rolled back.
- Canonical production deployment initially matched GitHub main at `4a91a3f`.

## Fixed during QA

- Capture preserves entered text, offers an editable title, and saves notes rather than a canned equipment idea. Stable Capture UUID and server primary-key handling prevent repeated-request duplicates; server title comparison requires an explicit separate-item override.
- Due Soon is today through seven calendar days. Closed work no longer appears in attention merely because it is old. Review items and overdue items qualify for attention. The date is current.
- Drawer saves through one mutation, honoring a cancelled completion confirmation. Completion/archive timestamps derive from the requested status on the server.
- Details query failures produce errors and retry controls, instead of empty tags/links/history. Failed deletes and lookups are checked. Missing records cannot return phantom update success.
- Re-linking a source preserves its primary flag. Primary switching validates the target before clearing anything and attempts restoration if setting fails. Removal derives primary state from the stored link, not the browser's stale flag.
- Incoming relationships invert directed labels. Removing one edge refreshes summaries so another edge between the same items remains visible.
- Verified authorized-account claims apply to every data endpoint. Expired API sessions return 401; the client returns to sign-in. Refreshed cookies survive proxy redirects; authenticated responses use private/no-store.
- Auth callback enforces the owner account and same-origin redirect. Mutation API rejects mismatched origins and validates IDs, dates, enum values, title, and editable columns. User ownership and server timestamps cannot be reassigned by a patch.
- Activity failure is reported as a warning after a committed change, rather than hidden or falsely causing UI rollback. Successful activity entries are generated by the server.
- Removed stale AI answers, hardcoded duplicate suggestions, fictitious workflow progress, unused mock inventory, unused browser Supabase client and three obsolete parallel APIs.
- Added dialog roles, field labels, keyboard focus containment/restoration, Escape close, focus outlines, empty states and smaller-screen layout fixes. Drawer no longer resets unsaved fields when relational details refresh.
- CI uses the committed lockfile and runs regression tests before building.

## Remaining issues

- Release is blocked pending user approval to merge the reviewable PR and publish the canonical production deployment. Post-fix production acceptance must follow that deployment.

- Primary-source changes and activity writes are multiple requests, not a database transaction. Failures are surfaced and primary switching has compensation, but simultaneous tabs and partial outages can still cause inconsistent state. Use narrowly scoped SECURITY INVOKER database functions with ownership checks and row locks before AI-assisted writes.
- Exact-title comparison across different Capture IDs is advisory and can race between tabs. Stable-ID retry protection is atomic via the existing primary key. Deliberate same-title items remain supported.
- Supabase security advisor warns that leaked-password protection is disabled. Enable it in the existing project's Auth settings when supported by its plan. No auth setting was silently changed.
- No workflow execution interface exists yet; the view now states that limitation accurately.

## UX improvements worth considering

- Show attention reasons and an expandable full attention list; the executive summary deliberately shows five items.
- Add unsaved-change confirmation, stronger inline save/error messages, and better small-screen navigation.
- Preserve view/filter state in the URL, improve large inventories with pagination, and eventually include all context in search.

## Technical debt

- Large page component and loosely typed API payloads should be split and typed before extending the reasoning layer.
- Work item mutation and activity need one transaction. Sources lack a database uniqueness constraint for one primary per item; introduce it with transactional mutation functions.
- RLS checks link-row ownership, but foreign keys do not enforce owner consistency between linked entities. The account gate and single user bound current exposure. Strengthen this before any multi-user expansion.
- The initial nine unused-index notices decreased to three after QA traffic. These performance notices are informational for this new, tiny database. Do not remove useful foreign-key/status indexes solely on current usage.
- Session expiry, network failures and concurrency should also be tested in an automated browser harness once the current live acceptance pass is complete.

## Ready / not ready for the AI layer

Not ready for autonomous AI writes. A constrained read-only reasoning pilot is the next phase once production acceptance is complete. Transactional mutations are a prerequisite for later accepted proposals changing inventory.

## Exact next build phase: Phase 4A, source-backed read-only reasoning

1. Add one server-only reasoning endpoint behind the same authorized session. Keep all OpenAI credentials server-only and select the model after checking current OpenAI documentation at implementation time.
2. Give the model only owner-scoped read tools: search work items, retrieve an item with tags/relationships/sources/history, and obtain deterministic counts/attention signals. Do not enable write tools or embeddings.
3. Return a validated structured result with a short answer, cited work-item IDs, reasons, uncertainty, and proposed next actions. Validate cited IDs against the retrieved data. Distinguish external source pointers from files actually read.
4. Start with: what deserves attention today, what is blocked, which existing work overlaps this idea, and weekly review. Never invent projects or stale workflow progress.
5. Display read-only recommendations alongside the existing app. Suggestions do not change inventory. Add rate limits, timeouts, usage caps, error handling and privacy-aware logs.
6. Evaluate against representative seeded cases: completed/parked items, near/far dates, missing actions, directed relationships, duplicate titles, missing sources, unauthorized requests, stale context and prompt injection in notes. Compare results against deterministic logic and cite only current records.
7. After the read-only pilot, Phase 4B adds persisted reviewable proposals. Only an explicit user acceptance may invoke the hardened transactional server mutation path. No autonomous changes, external messages or file moves.
